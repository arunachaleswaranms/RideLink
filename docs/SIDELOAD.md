# Sideload builds — Android and iOS

REQUIREMENTS §13 (Phase 8: "repeatable sideload builds"), STATUS §4 problem 107,
[ADR-029 Amendment A2](DECISIONS/ADR-029-release-hardening.md#amendment-a2--27-september-2026--diagnostics-export-and-sideload-provenance).

RideLink is never published to a store. The two phones run builds made on the developer's own Mac.
A build used for physical qualification must be **traceable to exactly one commit**, and this
procedure is what makes that true. An IDE build is fine for development, but it cannot be used as
evidence: its diagnostics export says `source_revision: unrecorded`.

**Never commit, print, paste or attach signing material** — keystores, key passwords, certificates
with private keys, provisioning profiles. `.gitignore` already excludes `*.p12`, `*.jks`,
`*.keystore`, `*.pfx`, `*.mobileprovision` and `keystore.properties`, and the procedure below keeps
all of it outside the repository anyway.

## Android (OnePlus Nord 5)

Everything goes through [`tools/sideload/android.sh`](../tools/sideload/android.sh). It needs JDK 21
(set `RIDELINK_JAVA_HOME` if it is not at Homebrew's `openjdk@21` path), the Android SDK build-tools
(found from `ANDROID_HOME` or `android/local.properties`), `adb`, and the macOS `security` tool.

### 1. Create the signing key — once per Mac

```sh
tools/sideload/android.sh keystore
```

This creates an RSA-3072 key in a PKCS12 keystore at `~/.ridelink/sideload/android-sideload.p12`
(directory mode 700, file mode 600; override the directory with `RIDELINK_SIDELOAD_HOME`). The
keystore password is 192 random bits (48 hex characters), generated by the script and stored in the **login
Keychain** under the service `ridelink-android-sideload`. It is never shown, and it never appears as a
process argument: it reaches `security` and `apksigner` through stdin, and `keytool` through its
environment. The script refuses to overwrite an existing key, because a phone only accepts an update
signed by the key that signed the installed build.

**Back the key up yourself, outside the repository**, if you want to keep updating an installed
build after the Mac is replaced. If it is lost, the only way forward is a clean install on the
phone, which erases RideLink's data and trust, and a fresh pairing.

### 2. Build, sign and verify one commit

```sh
git status                      # must be clean — the script refuses otherwise
tools/sideload/android.sh build
```

The script runs these steps, in order:

1. refuses a dirty working tree (tracked or untracked);
2. runs `:app:assembleRelease` with `-Pridelink.sourceRevision=$(git rev-parse HEAD)`. The app's
   Gradle file accepts only a full 40-hex lowercase commit, and compiles it into
   `BuildConfig.SOURCE_REVISION`;
3. `zipalign -P 16 4` (16 KiB page alignment for the native WebRTC libraries), then
   `apksigner sign` (APK Signature Scheme v2/v3 for `minSdk 31`), then `apksigner verify` and
   `zipalign -c`;
4. writes `android/app/build/sideload/ridelink-android-<sha12>.apk`, and a provenance record next to
   it, `ridelink-android-<sha12>.provenance.txt`: source revision, APK SHA-256, signer-certificate
   SHA-256, version name and code, build-tools and JDK, and build time. The record contains no path,
   no key material and no password. Copy it into the evidence document for the run.

The release build type is **not debuggable** (`run-as` and a debugger do not work). That is
deliberate, because it is the build the rider uses. Diagnostics come from the in-app export (below)
and from `adb shell dumpsys`.

To re-check any APK later:

```sh
tools/sideload/android.sh verify android/app/build/sideload/ridelink-android-<sha12>.apk
```

### 3. Install on the phone and prove what was installed

```sh
adb devices -l                                   # identify the PHYSICAL serial
tools/sideload/android.sh install -s <serial> android/app/build/sideload/ridelink-android-<sha12>.apk
tools/sideload/android.sh install -s <serial> --clean <apk>   # clean install: ERASES RideLink data and trust
```

- An explicit `-s <serial>` is required. Wireless debugging often lists the same phone twice (an
  `ip:port` transport and an mDNS `adb-…._adb-tls-connect._tcp` one). Both report the same
  `ro.serialno`, and either can be used.
- The script refuses an emulator (`ro.boot.qemu` set).
- It never passes `-g`. Runtime permissions (microphone, notifications) are granted only through the
  app's own prompts, because those prompts are under test.
- After installing, it **pulls the installed `base.apk` back from the phone** and requires its
  SHA-256 to equal the built APK's. It then prints the install record: mode (clean or update), time,
  serial, model, build fingerprint, `versionName`/`versionCode`, and `lastUpdateTime`.
- An update (`install -r`) keeps RideLink's data and trust. A record must say which one was used.
  Never describe an update as a clean install.

### 4. Confirm the build from the phone itself

Open **Show connection diagnostics → Export diagnostics log**. The header's `source_revision` must be
the commit in the provenance record. `unrecorded` means the build did not come from this procedure.

## Diagnostics export (NFR-08) — both platforms

**Show connection diagnostics → Diagnostics log → Export diagnostics log** hands the process's redacted
event log (the latest 1,024 events, ADR-029 §2) to the system share sheet as
`ridelink-diagnostics.txt`. RideLink sends nothing on its own: the user chooses where it goes (Files,
AirDrop, Nearby Share, a mail draft and so on) or cancels. There is no new network path.

The export contains only:

- a provenance header — platform, app version, source revision, export time as a *monotonic*
  timestamp;
- the event lines, already redacted by construction: `peer_id`, `identity_spki_sha256`,
  `conn_tiebreak` and the discovery handle are cut to 6 characters, and paths are cut to their
  basename.

SAS codes, TLS secrets, exporter output, bulk tokens and key material have **no log path**, so they
cannot be in an export. Audio is never logged. The unit tests pin both halves (ADR-029 Amendment A2).

On Android the text is written to one file in the app's private cache, which the next export
overwrites. It is readable by the chosen target only through a per-share grant on a non-exported
`FileProvider`. On iOS the text is produced in memory when the share target asks for it.

## iOS (iPhone 17 Pro Max) — personal team

> **NOT EXECUTED — REQUIRES PHYSICAL IPHONE.** No iPhone has been available (STATUS §4 problem 16).
> The only parts verified on this Mac are the unsigned device build and the revision stamp (Xcode 27,
> 27 September 2026). Signing, installation and every on-phone step are Phase 9B.

A free Apple ID "personal team" is enough, with two limits: a provisioning profile expires after
**7 days** (re-run the install), and the bundle identifier must be unique to the team.

1. Xcode → Settings → Accounts: add the Apple ID. Note the team ID (Xcode shows it; it is not a
   secret, but keep it out of the repository, because it is personal).
2. On the iPhone: Settings → Privacy & Security → **Developer Mode** on (this restarts the phone).
   Connect it by cable and trust the Mac.
3. From a clean tree, build a signed device build carrying the commit:

   ```sh
   git status   # must be clean
   xcodebuild -project ios/RideLink.xcodeproj -scheme RideLink -configuration Release \
     -destination 'generic/platform=iOS' -derivedDataPath build/ios-sideload \
     -allowProvisioningUpdates DEVELOPMENT_TEAM=<team-id> \
     PRODUCT_BUNDLE_IDENTIFIER=<unique.reverse.dns.id> \
     RIDELINK_SOURCE_REVISION="$(git rev-parse HEAD)" build
   ```

   `RIDELINK_SOURCE_REVISION` expands into the app's `RideLinkSourceRevision` Info.plist key. If
   it is left unset, the key is empty and the export says `unrecorded`.
4. Install and identify it:

   ```sh
   xcrun devicectl list devices
   xcrun devicectl device install app --device <device-id> \
     build/ios-sideload/Build/Products/Release-iphoneos/RideLink.app
   ```

5. On the phone, the first launch asks you to trust the developer: Settings → General → VPN & Device
   Management. RideLink then asks for Local Network access when discovery starts, and for the
   microphone when the intercom starts. Grant or deny them through those prompts, because they are
   under test.
6. Confirm the build: **Export diagnostics log** → `source_revision` must equal the commit.

`DEVELOPMENT_TEAM` and `PRODUCT_BUNDLE_IDENTIFIER` are passed on the command line, so the repository
never records a personal team or identifier.
